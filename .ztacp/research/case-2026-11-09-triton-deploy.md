# Research Case: triton-deploy (E15/I39 — регистрация при Genesis)

- **Дата открытия:** 2026-11-09 (UTC)
- **Проект:** triton-deploy — школьное задание: деплой CV-моделей (ResNet50 + YOLOv5) на NVIDIA Triton Inference Server, Docker, Prometheus/Grafana.
- **Режим:** School Mode (6.16) поверх Solo Mode (6.14). Уровень зрелости: **L1** (закон-в-файлах, стен = C5-стейджинг + паритет дерева I51 + карантин кред I52).
- **Конфигурация:**
  - P-1 — человек-принципал (студент), второй ключ, арбитраж.
  - S-1 — координатор: opencode / GLM (`opencode-glm-coord`), держатель lease.
  - W-1..W-4 — воркеры-сабагенты одной сессии координатора (модели / деплой / мониторинг / клиент). Клон один, коммиты зон сериализует координатор (C5 сохранён точным стейджингом, атрибуция зоны — в сообщении).
- **Вендоры:** один вендор (GLM) во всех ролях — зафиксирован риск коррелированных слепых зон (6.14.3); компенсация: контракты-швы до параллелизма (B1) + машинные проверки (check-tree.sh, стерильность-скан) вместо суждений.
- **Окружение:** CPU-only (GPU нет → ONNX-бэкенд по заданию), Docker Desktop, GitHub как хост (замена Gitea) — по прямому приказу P-1.
- **Исследовательские вопросы:** RQ1 (эффективность конституции L1 в соло-сборке с сабагентами), RQ4 (цена governance: сериализация коммитов, карантин кред против скорости), продолжение корпусу brain-check/forte-vision.
- **T-final:** стерильная ветка `submit` (I53) — этап 9 плана.

- Зоны W-1..W-4 выполнены сабагентами одной сессии; сериализация коммитов координатором — 0 конфликтов стейджинга (C5 выдержан, зона атрибутирована в сообщениях).

- RQ4: цена governance — ~6% времени (коммиты/план/журналы), выгоды: сабагенты не столкнулись путями; ошибка версии API поймана живым прогоном.

## 4. Наблюдённые failure modes (новое для корпуса)

1. **Деградация не.Options, а сборки**: dynamic int8 валиден по onnx.checker и локальному ORT, но не грузится сервером → вывод: верификация модели обязана идти В целевом рантайме (живой load), локальная проверка недостаточна. Урок в план будущих кейсов: W-зоны верифицируют локально, S-1 — интеграционно на живом стеке.
2. **Сель-хост порт-конфликты**: два разных держателя 8000 (процесс и контейнер) — нужны в контракте портов не только порты стека, но и пред-чек занятости (добавить в run_triton.sh не успели — в backlog).
3. **Медленная сеть как доминанта времени**: 50 мин pull против ~5 мин работы — кейс подтверждает I56 (хост/образ резервируются на старте).
4. **Собственные инструменты тоже дрейфят**: 6 багов в check-tree/sterile-branch пойманы только потому, что они запускались как механические проверки. Мораль: governance-код = код, ему нужны свои прогоны.
5. **Один вендор во всех ролях**: обошлось без коррелированных слепых зон из-за живых проверок; риск остаётся (все агенты одинаково не знали метрики Triton 23.12 — нашла только живая сверка).
6. **msg-фильтрация истории**: кавычки eval в filter-branch — хрупкое место; финальная версия скрипта прошла 3 итерации. Ролевые следы в сообщениях снимаются правилами, но требуют ручной сверки вывода.

## 5. Выводы по исследовательским вопросам

- **RQ1 (снижает ли конституция L1 нарушения?):** да, третья зелёная точка: 0 инцидентов при 4 параллельных зонах и 7 сабагент-запусках. Но уточнение: в соло-сборке зоны НЕ столкнулись ни разу — конституция работала как координационный протокол (контракты до параллелизма), а не как запретительная стена; главный защитник — машинные проверки (check-tree, live-verify).
- **RQ4 (цена governance):** ~6% времени (план, журналы, аттестации, сериализация коммитов) против найденных 5 живых ошибок интеграции и 6 багов инструментария — соотношение выгоды/цены высокое.
- **Новое предложение для канона (кандидат, не инвариант):** «верификация артефакта в целевом рантайме» (live-verify) как обязательный шаг приёма зоны, когда зона производит рантайм-зависимые артефакты (модели, конфиги) — локальная валидация недостаточна (failure mode №1).
